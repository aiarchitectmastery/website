AAM Agent Workflow

By Ari Vilkman, AI Architect

Your repository, your rules, with you as the final gate. A free template repository for the AI Driven Development Methodology (PRD → PLAN → TASK → IMPLEMENTATION), plus a three-day email guide through your first cycle.

Get the template

Free. Plain Markdown files. No installer, no course purchase.

Current release: BETA 2.0.0. BETA means the AAM Agent Workflow is ready to use on real projects today and is still evolving: new releases refine its templates and prompts based on real use.

Who it is for

You build software for a living, and you already use GitHub Copilot or another AI agent. The usage works, but it is ad hoc: each session starts from scratch, and the result depends on how you happened to prompt that day. AAM Agent Workflow gives that work a structure you can review, so AI-generated changes meet the same standard as code a colleague wrote.

What it is

AAM Agent Workflow is a set of plain Markdown files that live in your own repository: the PRD → PLAN → TASK → IMPLEMENTATION workflow, templates for the PRD, PLAN and TASK, an IMPLEMENTATION review checklist and reusable prompts. It is the AI Driven Development Methodology in practice. You stay the architect at every checkpoint. The AI agent is the builder.

It works with GitHub Copilot and with other AI agents that can read files in your repository.

What it is not

  • Not an agent, installer or tool to configure. You copy files, and nothing runs on its own.
  • Not a runtime control. The files do not enforce permissions, so keep using your environment's permission controls.
  • Not a guarantee of correctness or productivity. Quality still depends on the task, your verification and your judgment.

What's inside

A simplified view of the folder structure:

.
├── .aam/                              ← the reusable workflow
│   ├── workflows/core-workflow.md     ← start here: the procedure
│   ├── templates/
│   │   ├── PRD-template.md
│   │   ├── PLAN-template.md
│   │   ├── TASK-template.md
│   │   ├── bounded-task-template.md
│   │   └── IMPLEMENTATION-checklist.md
│   └── prompts/
│       ├── fresh-session-handoff.md
│       └── agent-guidance-review-prompts.md
└── agent-workflow/                    ← your own PRDs, PLANs and TASKs go here
  • core-workflow.md: the four phases, six steps and the mandatory human checkpoints
  • PRD-template.md: capture intent, scope, constraints and acceptance criteria
  • PLAN-template.md: turn an approved PRD into ordered tasks with checkpoints
  • TASK-template.md: delegate one bounded task with context, constraints and verification
  • bounded-task-template.md: a short brief and a read-only gap check before any edits
  • IMPLEMENTATION-checklist.md: the human review before anything merges, with an evidence-based verdict
  • fresh-session-handoff.md: move work to a fresh conversation without losing verified context
  • agent-guidance-review-prompts.md: review existing agent instructions one approved change at a time

The four phases

  1. PRD: define what will change and what will not, the constraints and the acceptance criteria. Approve it yourself.
  2. PLAN: turn the approved PRD into ordered steps with checkpoints. Review the approach before any work is delegated.
  3. TASK: delegate one bounded task with context, constraints, stop conditions and the checks to run.
  4. IMPLEMENTATION: review the result against evidence (scope, tests, conventions, security and edge cases) and record your decision: accept, revise, reject, reassign or return. Acceptance does not authorize release or deployment.

Read the vendor-neutral definition in the AI Driven Development Methodology reference, or see how the review works on the IMPLEMENTATION phase page.

Three ways to start

  • New project: create a new repository from the template.
  • Existing project: copy the .aam/ and agent-workflow/ folders into your repository. Never overwrite files you already have.
  • ZIP: download it from the latest release and copy the folders.

The README in the repository has the exact steps for each path.

Why this works

  • Architectural control: you own the intent, the plan and every decision. The agent performs bounded work.
  • Evidence before acceptance: checkpoints help expose issues. They do not guarantee production readiness or authorize release.
  • A repeatable structure: the same files work across languages and frameworks, and your teammates can follow the same workflow.
