AI Driven Development Methodology

The AI Driven Development Methodology is AI Architect Mastery's human-led, vendor-neutral operating model for building production-quality software with AI agents. Its canonical workflow is PRD → PLAN → TASK → IMPLEMENTATION. The human remains the architect; AI agents act as bounded builders.

Structured Vibe Coding is AAM's secondary name for this same method, not a competing workflow. This reference is for developers and architects who want explicit intent, reviewable delegation and evidence rather than ad hoc prompting.

Updated 2 October 2026 · Source: AAM Methodology, master definition v1.1 · Editorial owner: AI Architect Mastery

Three views of one operating model

1. Responsibility: Human as Architect → AI as Builder
The human owns intent, boundaries and acceptance. The human-led model explains what is delegated and what remains human-owned.
2. Decision model: DEFINE → DELEGATE → BUILD → VERIFY
The four-action decision model makes the method memorable without renaming or replacing the Core phases.
3. Artifacts and evidence: idea → PRD → PLAN → TASK → IMPLEMENTATION → evidence
The Core workflow makes intent and execution inspectable. Lowercase idea and evidence are boundary concepts, not extra mandatory phases.

The four-phase Core workflow

Each phase has a distinct job. AI may propose artifacts and perform work; the Human Architect reviews the decisions that authorize progression.

  1. 01 · PRDCapture intent and acceptance criteria
  2. 02 · PLANStructure dependency-aware work
  3. 03 · TASKDelegate one bounded Work Item
  4. 04 · IMPLEMENTATIONBuild, verify and decide

Review and testing belong inside IMPLEMENTATION. Controlled iteration returns work to PRD, PLAN or TASK when evidence shows an earlier decision needs correction.

Explore the methodology in six reading groups

These groups organize the reference; they are not six new workflow phases or the three views above. Each linked concept has one canonical home.

1. Establish the human-led model

Understand accountability, the decision model and the environment for delegated work.

  • Human as Architect, AI as Builder
  • DEFINE, DELEGATE, BUILD, VERIFY
  • Selected context and the Agent Harness

2. Define intent and plan the change

Make requirements testable and the implementation approach reviewable.

  • PRD: capture intent
  • Acceptance criteria
  • PLAN: structure the work
  • Review a plan before delegation

3. Delegate bounded agent work

Give one responsibility the context, permissions and verification it needs.

  • Agent, Role, Skill, Capability and Tool
  • TASK: bounded known work
  • Work Products and Work Items
  • Autonomy boundaries
  • Reliable task handoff

4. Build, verify and decide

Inspect the actual change and accept or return it using evidence.

  • IMPLEMENTATION: build and verify
  • Bugs and state-aware evidence
  • Scoped BUG correction
  • The human implementation checkpoint

5. Diagnose uncertainty and return

Distinguish known work, defects and uncertain assumptions before choosing a correction.

  • Controlled iteration and return decisions
  • TASK, BUG and PROB
  • Refresh dependencies and revalidate the claim

6. Adapt and apply

Keep methodology semantics stable while tools, permissions and execution environments vary.

  • Runtime adaptation
  • Verify native runtime execution
  • Wider process context
  • Choose your next bounded change

How AAM Agent Workflow relates to the method

AAM Agent Workflow operationalizes the methodology through stages, agents, work products, handoffs and checkpoints. It is not a second methodology. The Agent Model describes responsibilities and abilities; Work Items describe actionable work; the Agent Harness supplies the operating environment.

Runtime adaptation expresses those semantics through native conventions. A defined concept or reference structure is not evidence of a released installer, adapter, extension or plugin.

Constructed example: a bounded export change

A team wants an existing export to reject unauthorized access. The PRD defines who may export and what must remain unchanged. The PLAN sequences authorization and regression checks. A TASK delegates the scoped correction. IMPLEMENTATION reviews the diff and tests both allowed and denied requests.

If the team discovers that ownership of shared records was never defined, the human returns to the PRD instead of asking the agent to invent a policy. This is an illustration, not a reported project outcome.

Terminology and canonical homes

This registry fixes where terms are defined. Follow the canonical home for scope, relationships, examples and limitations.

AI Driven Development Methodology / Structured Vibe Coding
AAM's operating model and its secondary name; this overview is their shared canonical home.
AAM Agent Workflow
The operational view of the methodology, defined above; not a claim of product availability.
Human Architect / AI Builder
The responsibility model, not a transfer of accountability to AI.
DEFINE / DELEGATE / BUILD / VERIFY
The memorable decision model; the artifact Core retains its own names.
PRD / PLAN / TASK / IMPLEMENTATION
The four canonical Core phases and their distinct work products or decisions.
Agent / Role / Skill / Capability / Tool
The conceptual Agent Model; tool availability does not prove capability.
Selected context / Agent Harness
Relevant knowledge and the operational environment that provides or constrains agent work.
Work Product / Work Item
A workflow artifact and its actionable subset.
Work Type: TASK / BUG / PROB
Sibling classifications for known work, established failure and uncertainty. TASK's full definition remains on its Core page.
Acceptance criteria
Observable expectations against which the human evaluates a result.
Autonomy boundary
The permitted independent decisions and conditions that require returning control.
Evidence
The observable basis for a decision, tied to the state that was actually checked.
Human Checkpoint
The evidence-backed ACCEPT, REVISE, REJECT, REASSIGN or RETURN decision.
Controlled iteration / Return
A human-directed correction of an earlier PRD, PLAN or TASK decision.
Refresh and revalidate
Update dependent work and restore evidence after an earlier decision changes.
Runtime / Adapter
The execution environment and the semantic adaptation boundary, not guaranteed feature parity.
