AI Driven Development Methodology

The AI Driven Development Methodology is AI Architect Mastery's human-led, vendor-neutral operating model for building production-quality software with AI agents. The human owns intent, architecture and acceptance; AI performs bounded work. Its canonical Core is PRD → PLAN → TASK → IMPLEMENTATION.

Instead of treating generated output as finished work, make intent explicit, delegate within limits and decide using evidence. This map explains the model first, then shows where to examine its supporting concepts.

Three levels of the same methodology

Level 1 · Responsibility Model

Human as Architect → AI as Builder

The human owns intent, direction, architecture, delegation, boundaries, evidence evaluation and the final decision. AI agents perform delegated work within that direction. Delegating execution never delegates accountability.

Explore the responsibility model

Level 2 · Operating Model

DEFINE → DELEGATE → BUILD → VERIFY

Clarify the intended result, authorize bounded work, build within scope, then evaluate what was produced. These are the actions through which the human directs agent work, not four workflow phases or a replacement for the Core.

Explore the operating model

Level 3 · Core Workflow

idea → PRD → PLAN → TASK → IMPLEMENTATION → evidence

The canonical Core is PRD → PLAN → TASK → IMPLEMENTATION. Lowercase idea and evidence are boundary concepts, not extra Core phases.

  1. 01 · PRDDefine intent, scope, constraints and acceptance criteria.
  2. 02 · PLANTurn approved intent into a reviewable approach.
  3. 03 · TASKDelegate one bounded, authorized assignment.
  4. 04 · IMPLEMENTATIONBuild, review, test and make a human decision.

Review and testing belong inside IMPLEMENTATION. They are not delayed until a separate phase after the Core.

Evidence, Human Judgment and Human Checkpoints

Agent claim ≠ Evidence. An agent can report success. Evidence is observable information, such as a reviewed change or a test result, that supports or contradicts that claim.

Human Judgment is the evaluation of that evidence against intent, constraints and remaining risks. A Human Checkpoint is a meaningful decision point: ACCEPT, REVISE, REJECT, REASSIGN or RETURN. It does not require the human to approve every agent micro-action.

Human Governance connects these responsibilities: define delegation and autonomy boundaries before work, evaluate evidence and apply Human Judgment at a checkpoint.

Controlled Iteration: correct the earlier decision

When implementation evidence reveals a wrong assumption, the human chooses where the work belongs: PRD for missing intent, PLAN for an inadequate approach or TASK for an insufficient assignment. Correcting code alone cannot resolve an undefined requirement.

Evidence → Human Judgment → return to PRD / PLAN / TASK → refresh dependent work → revalidate.
This is a controlled return within the methodology, not another mandatory workflow phase.

Explore Controlled Iteration and what must be refreshed and revalidated. A known defect within valid scope can be corrected without returning to an earlier decision.

Supporting framework: AAM Agent Workflow

Agent Workflow operationalizes this methodology; it is not a second methodology. The following supporting views describe how responsibilities become bounded work. They sit beneath the three-level model, not alongside it as alternative workflows.

Human Governance
Human-owned delegation, boundaries, evidence evaluation and acceptance across the workflow.
Agent Model
The actor, responsibility and abilities needed for delegated work.
Agent Harness
The operational environment that provides context and constrains execution.
Work Model
Work Products record decisions and outputs; Work Items carry actionable assignments.
Runtime / Adapter
Native mechanisms express the model in a particular execution environment.
Controlled Iteration
Human-directed return, refresh and revalidation when an earlier decision needs correction.

AAM defines WHAT; runtime / adapter defines HOW. Responsibilities, work products and acceptance remain stable while tools and permissions vary. Runtime adaptation does not imply equal capabilities or an available AAM adapter, installer or plugin.

Wider Process Context

Before the Core, idea → blueprint → optional prototype → PRD can help clarify uncertainty. After implementation, evidence → human checkpoint → release connects acceptance to the wider delivery process.

These activities do not add mandatory Core phases, move verification outside IMPLEMENTATION or authorize automatic release. Explore the wider process context.
