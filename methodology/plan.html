PLAN: turn intent into structured work

A PLAN turns an approved PRD into a dependency-aware, reviewable implementation approach with explicit completion conditions and checkpoints. It explains what should happen in what order before the work is delegated to agents.

PLAN is the second Core phase of AI Architect Mastery's AI Driven Development Methodology. It connects approved intent to bounded TASKs.

Updated 2 October 2026 · Source: AAM Methodology v1.1, §4.2 · Owner: AI Architect Mastery

Why this comes before TASK

An agent asked to "just build the PRD" in one pass can produce a large, hard-to-review diff. A PLAN divides the approach into reviewable increments and exposes architectural decisions before implementation makes them expensive to undo.

Skipping directly from intent to code leaves sequencing choices implicit. Even a reasonable local choice can conflict with constraints that the agent has not considered.

What a working PLAN defines

  • What gets built first and why: dependency order, not arbitrary order.
  • Which PRD requirements map to which planned steps.
  • Where meaningful checkpoints occur before downstream work depends on a decision.
  • What done means for each step, not only for the whole feature.

Inputs, output and responsibility

Input: the approved PRD and relevant architecture and code context. Output: a reviewed implementation approach with steps and completion conditions. Owner: the Human Architect reviews and approves the approach; the agent may propose it.

In practice, the human can ask an agent to propose a plan, then edit and approve it before TASKs begin. Plan review checks coverage, dependencies, scope and verification, not merely whether the list sounds plausible.

Constructed example: sequence an authorization change

The approved PRD requires owner-only export. The PLAN identifies the existing authorization helper, sequences the scoped handler change and specifies allowed/denied request checks plus output-format regression evidence. It does not bundle an unrelated reporting rewrite into the first step.

Planning is not a guarantee

Implementation can reveal that the approach cannot satisfy an approved constraint. Use a controlled return to PLAN, revise the approach and refresh dependent TASKs. Do not let an obsolete plan justify unapproved agent improvisation.

Related concepts

  • Plan review establishes readiness for delegation.
  • Acceptance criteria anchor the completion conditions.
  • Task handoff carries one approved step into execution.
  • Refresh and revalidate updates downstream work when the approach changes.
