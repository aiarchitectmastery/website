IMPLEMENTATION: build, verify and decide

IMPLEMENTATION combines bounded agent execution with review, tests, evidence and a human decision about whether the change is acceptable. The agent's output is a draft, not a delivery; generating code is only part of the phase.

This is the fourth Core phase of AI Architect Mastery's AI Driven Development Methodology. It takes an authorized TASK and checks the result against its scope and the underlying PRD.

Updated 2 October 2026 · Source: AAM Methodology v1.1, §§3, 4.4 · Owner: AI Architect Mastery

Why generation is not completion

A result can compile or look correct while violating a requirement or introducing architectural drift. Keep the same review discipline expected of any contributor. Production quality does not depend on whether a human or an agent wrote the first draft.

Nothing merges without human review. Testing and review belong inside IMPLEMENTATION and its acceptance model; they are not fifth and sixth mandatory Core phases.

What implementation review checks

  • Does the actual change satisfy the TASK and stay within its scope?
  • Do tests and other evidence demonstrate the required behavior?
  • Does the result follow project conventions and architectural direction?
  • Have security, performance, relevant edge cases and regressions been evaluated?
  • Which claims remain unverified, and what risks or limitations must the human consider?

Inputs, output and responsibility

Input: an authorized TASK and its selected context. Output: a reviewed change, verification evidence and a human verdict. Owner: the agent executes within scope; the human owns evidence evaluation and acceptance.

A Human Checkpoint can result in ACCEPT, REVISE, REJECT, REASSIGN or RETURN. Human Judgment evaluates the evidence behind that decision. Checkpoints are meaningful decision boundaries, not approval of every micro-action; acceptance does not automatically authorize release or deployment.

Constructed example: review the whole export claim

The handler now calls the authorization helper. The reviewer inspects the diff, checks owner success and non-owner denial, and verifies that the original export format still holds. A confident summary or one successful request is insufficient evidence for that complete claim.

Explore build, verification and decisions

  • Bugs and state-aware evidence explains why plausible output is not proof.
  • Scoped BUG correction restores established behavior without opportunistic expansion.
  • Human implementation checkpoint makes the acceptance decision explicit.
  • Controlled iteration returns to PRD, PLAN or TASK when the issue belongs earlier.

When to correct and when to return

A known failure within valid scope calls for correction and revalidation. Missing intent, an inadequate approach or an insufficient assignment calls for a human-directed return to the appropriate artifact. After a return, refresh dependent work before continuing.
